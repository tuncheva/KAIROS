Engineering proposal · KAIROS AI

The agent that speaks first

KAIROS had four working agents, a hardened draft → confirm → apply lifecycle, and a bounded tool loop. What it lacked was reach, initiative, memory, and proof. This is the plan for all four — and the record of building it.

The gaps are not in the plumbing. They are in what the agent can see, whether it ever acts on its own, what it remembers, and whether anyone can tell if it is any good.

Diagnosis — what was missing

Four gaps

Gap one

Reach

A1 has eight read tools and no search. Whole categories of question are unanswerable by construction.

  • Cannot read a task comment, an org member list, a calendar range, a collaborator, an RSVP, or the activity log
  • “Where did we discuss the payment flow?” — no search tool exists
  • “Who is overloaded this week?” — no cross-project view of assignment

Gap two

Initiative

Every AI action begins with a human typing. The assistant never opens its mouth first.

  • No server-side scheduler exists anywhere in the codebase
  • EventReminderService.tsx is a client component — reminders only fire while a browser tab is open
  • No brief, no watch, no nudge, no follow-up

Gap three

Memory

Sixteen raw messages replayed, nothing summarised, nothing carried between conversations.

  • ai_conversations.title exists in the schema and is never written — there is no conversation list
  • No durable facts: it cannot know your sprint runs Mon–Fri
  • Long threads either lose their beginning or blow the context budget

Gap four

Proof

One AI test file. No eval set. Every prompt edit is a coin flip.

  • ai_messages stores model, tokens and latency on every row — and nothing reads them
  • citations is produced by the model and rendered nowhere in the UI
  • Five UI locales shipped, two agent languages supported
The work

Seven tracks

Track letters are the identifiers used by the roadmap below. Tracks A and F are foundations — everything else gets better once the agent can see more and quality can be measured.

A

Reach — give the agent eyesShipped

Eight read tools become eighteen, and one of them can search.

  • A-1 A searchWorkspace tool. Postgres full-text search (tsvector + GIN) across tasks, projects, unlocked notes, events and comments. No new infrastructure, no new dependency. Locked notes stay excluded at the query level, matching the existing three-layer rule. The single largest capability unlock available.
  • A-2 Expand the read-tool surface. Keep the design rule that already works — tools return computed answers, not rows for the model to count. getProjectDetail returns pre-computed overdue counts, and that is exactly why progress questions work today.
    New toolQuestion it makes answerable
    searchWorkspaceWhere did we discuss the payment flow?
    listMyWorkWhat is on my plate this week, across every project?
    getWorkloadByAssigneeWho is overloaded?
    listTaskCommentsWhat has the team said about this?
    getTaskActivityWhat changed on task 42 since Monday?
    listOrgMembersWho is in the Design org, and in what role?
    listProjectCollaboratorsWho can edit this project?
    getCalendarRangeWhat is due Monday to Friday?
    listNotesMetadataDo I have notes about this?
    listEventRsvpsWho is coming to the kickoff?
    getProjectHealthVelocity, overdue clusters, unassigned share
  • A-3 Raise the loop ceiling. Six iterations is tight once eighteen tools exist. Raise A1 to eight, and run independent reads in parallel — the sequential note in toolLoop.ts cites pool pressure and id chaining, neither of which applies to calls that do not depend on each other.
B

Initiative — the headlineShipped

This is what separates a chatbot in the corner from an assistant.

  • B-0 A scheduler, first — nothing else in this track is possible without one. Preferred: ws-server/ gains a scheduler. It is already a long-lived Node process with database access and a socket channel to push results, so it is the least new infrastructure — and it fixes the browser-only event reminders as a side effect. Alternatives are Vercel Cron against an authenticated internal route, or a separate worker.
  • B-1 Daily Brief — a new read-only agent, A6. Reuses A1's tool registry and skips the draft lifecycle entirely, because it never writes. Delivered as a notification, a dashboard card, and optionally email through the Resend integration that is already wired.

    3 tasks due today. Project Alpha slipped two days — the API work is the blocker. Maria has not been assigned anything this sprint. The kickoff has 4 unanswered RSVPs.
  • B-2 Risk Radar. A scheduled pass over each active project flagging overdue clusters, unassigned tasks, tasks with no acceptance criteria, a completion rate that has flatlined, an event with a date but no description. Emits notifications — never writes.
  • B-3 Nudges that arrive pre-drafted. Every proactive item ships with a drafted fix rather than a complaint. The draft/confirm/apply machinery supports this as-is — the only change is that a watcher creates the A2 draft instead of a chat turn. This is the feature that makes the system feel like it is working for you.

    Task #42 is six days overdue and unassigned → assign to Ivan, push to Friday? [ Apply ]
  • B-4 Quota and consent. A new ai_schedules table, the rate limit split into interactive and system buckets, and a per-feature toggle in settings that is off by default. Proactive runs must never eat the budget a person was going to spend themselves.
C

Memory — an assistant that knows youShipped

The cheapest track here, and the one that most changes how the product feels.

  • C-1 Rolling conversation summary. Past sixteen turns, fold the oldest half into ai_conversations.summary and replay summary plus the last eight. Long threads stay coherent instead of losing their beginning.
  • C-2 Durable user facts — a new ai_user_memory table. Written only through an explicit rememberFact tool that the user actually triggers, never silently inferred. Every row visible and deletable under Settings → AI Memory, capped at about twenty facts in the prompt.

    Sprint runs Mon–Fri. · Wants tasks written in Bulgarian. · Treats “urgent” as within 48 hours.
  • C-3 Conversation titles and a history browser. Generate title from the first turn with one cheap call — the column already exists and has never been written — then list past conversations in the chat sidebar with search.
D

Ambient — meet the work where it happensShipped

Every item below is a pre-filled runAgentTurn call with a seeded message and scope. No new plumbing.

  • D-1 Inline affordances. Task detail → break into subtasks, draft a status comment, why is this blocked. Project → risk radar on demand. Note → summarise, turn into tasks. Event → draft the description, find a time that clears the team's calendar. Notification bell → summarise what I missed.
  • D-2 Command palette with natural language. Type anything; if it does not match a navigation target, it becomes an agent turn. The highest leverage per line of code in this document.
  • D-3 Selection → AI. Select text anywhere — a note, a project description — and get turn into tasks, summarise, or translate.
E

Composition — multi-step work, and asking backShipped

One handoff per turn is the current ceiling. Real requests are not that shape.

  • E-1 Add a clarify intent. The intent schema allows answer, handoff and draft_plan, so an ambiguous request produces a guess. Add one question back plus two to four suggested chips. Good assistants ask; they do not guess.
  • E-2 Multi-agent turns. “Break down Project Alpha, note the risks, and schedule the kickoff” needs three handoffs; runAgentTurn executes exactly one. Make it an ordered handoffs[] capped at three, run sequentially, and render stacked confirm cards. Bounded, and still one request.
  • E-3 Refinement turns. “Change #3's due date to Friday and drop #7” should re-draft against the existing plan, not start over. Pass the current plan in as priorPlan and re-hash — the confirm token is already minted from the hash, so integrity holds automatically.
  • E-4 Finish A5, the Org Admin. Routing exists and the handoff currently returns “not available yet”. Same lifecycle as A2–A4, plus one rule: every write is dangerous and requires typed confirmation, because role changes have long-tail consequences. Already specified in the repository docs.
F

Proof — make quality measurableShipped

Until this exists, every prompt edit is a coin flip.

  • F-1 An eval harness — 60 to 100 golden cases. Run against recorded fixtures in CI, free and fast, and against the live model on demand. Two metrics matter: routing accuracy — did A1 pick the right agent — and schema validity rate — how often does JSON repair have to fire.
  • F-2 Authorization regression tests. For every read tool, assert it fails closed for a non-member. Audit finding P0 #1 was exactly this class of bug — an agent reading any project by id. One test per tool prevents its return.
  • F-3 An AI observability page. Every number is already stored in ai_messages and currently unread: p50 and p95 latency per agent, tokens per day, repair rate, tool failure rate, exhausted-loop rate, top failing tools.
  • F-4 Model tiering. One chain serves everything today. Route by job — a small, cheap model for classification, titles and JSON repair; the strong model for planning and analysis. chatCompletion already accepts a model, so this is a tier parameter and one new environment variable.
G

Polish — what users feel on day oneShipped

Small changes with an outsized effect on whether the assistant is trusted.

  • G-1 Stream the answer, not just the progress. Today the tool calls stream and the answer lands as one blob up to ninety seconds later. Split the response so the summary streams as text and the structured envelope arrives last. Perceived latency is the first complaint against any reasoning model.
  • G-2 Language parity. Five agent languages to match five shipped locales, driven by the user's saved language preference rather than the prompt guessing from message text. The prompt currently hardcodes English or Bulgarian.
  • G-3 Citations that click. The model already emits label and ref pairs, and the UI drops them on the floor. Render each as a deep link. Trust comes from being able to check the answer.
  • G-4 Suggested follow-ups. Two or three next questions returned with each answer — same call, one extra field. It is what keeps people using an assistant rather than trying one.
  • G-5 Undo. Every apply already writes a result JSON to an applies table. Add ten minutes of undo, reversing creates by id. The confidence to press Apply comes from knowing you can take it back.

Before committing

Decisions and risks

Background jobs need a home — and this one blocks all of Track B

Next.js route handlers do not run on a schedule. Choose between the ws-server/ scheduler, Vercel Cron, and a separate worker before Phase 2 starts.

Full-text search versus embeddings

Postgres FTS is free, needs no extension, and works today. pgvector buys semantic recall at the cost of an embedding call per write and a new extension. Ship FTS in Phase 1, then measure what search actually misses before deciding whether vectors earn their keep.

Proactive AI is a spend multiplier

One brief per user per day is a fixed daily cost with no human in the loop to justify it. Gate it behind explicit opt-in and an organisation-level quota.

Proactive AI is also a trust risk

An assistant that is wrong when you asked it is annoying. One that is wrong unprompted is noise you switch off permanently. Ship the Risk Radar behind a flag and treat dismissal rate as the primary metric.

The 50-per-day limit will bite

A multi-agent turn costs three to five model calls. Meter by calls rather than messages — recordExtraAiCall already exists for the tool loop, so extend it to the draft and handoff paths.

The documentation has drifted

The agent overview still describes code at src/server/agents/, which is now src/server/llm/. Fix it during Phase 1 or the plan inherits the confusion.

If there were only one week

Three things, in this order

  1. searchWorkspace The largest capability gain per line of code anywhere in this document.
  2. An eval harness with forty routing cases Turns prompt work from guesswork into engineering.
