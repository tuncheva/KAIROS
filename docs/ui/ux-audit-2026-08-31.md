# KAIROS — UX Audit

**Date:** 2026-08-31 · **Branch:** `development` @ `9535b5f` · **Method:** static read of every route, shell component and feature surface in `src/app` and `src/components`, cross-checked against the tRPC routers to find promised features with no entry point and entry points with no destination.

---

## Executive summary

KAIROS is not short on features. It is short on **feedback, consistency, and completed paths**. The product reads as three generations of UI layered on top of each other: a well-built recent tier (notes, chat, calendar, projects list), a middle tier (dashboard, events, settings), and an older tier (task timeline, project management, milestone timeline) that never got the same care. A user moving between them experiences three different products.

Four things dominate everything else:

1. **The app cannot talk to the user.** `ToastProvider` never renders its toasts. 126 `toast.success` / `toast.error` calls across 23 files are silently swallowed. Every save confirmation, every validation error, every failure message in KAIROS is invisible. This single defect makes almost every other flow feel broken, because the user gets no acknowledgement that anything happened.
2. **Several promised features have no reachable UI.** Project chat, AI undo, and full-text workspace search all exist as backend procedures (or as an orphaned component) with no caller. The README sells them.
3. **Several buttons lead nowhere.** The command palette ships three dead routes. The event Share button copies a URL nothing handles. The note-password reset email carries a token the page ignores.
4. **New users are not onboarded.** The role-selection gate is mounted on `/create` and `/notes` only — and sign-in lands on `/dashboard`. Most users never see it.

Nothing here is a rewrite. The fix list is long but almost every item is small and local. **Fixing items 1–8 below (~1–2 days) would change the felt quality of the product more than any new feature.**

### Fix roadmap

| Wave | Theme | Items | Effect |
|---|---|---|---|
| **1** | Make the app speak | P0-1 | Every existing flow starts confirming itself |
| **2** | Close the dead ends | P0-2 … P0-8 | No button lies; promised features become reachable |
| **3** | One shell, one nav | P1-9 … P1-17 | The app stops feeling like three apps |
| **4** | Mobile parity | P1-18 … P1-21 | The product becomes usable on a phone |
| **5** | Trust and polish | P1-22 … P2-49 | Preferences stick, modals behave, copy is localized |

## P0 — Broken. These make users think the product does not work.

### P0-1. No toast ever appears anywhere in the application

**Where:** [ToastProvider.tsx](src/components/providers/ToastProvider.tsx)

```ts
const [, setToasts] = useState<Toast[]>([]);   // value discarded
// ...
return <ToastContext.Provider value={api}>{children}</ToastContext.Provider>;  // no viewport
```

The state value is destructured away and the provider renders no toast surface. There is no `Toaster`, no toast viewport, and no `aria-live` region anywhere for toasts.

**Impact:** 126 call sites in 23 files produce nothing. Concretely, a user gets zero feedback when they: create/delete a project, join an organization with a code, copy an invite code, save a note, share a note, delete a notebook, create/update an event, switch workspaces, change appearance, or hit any server validation error. The most damaging case is the **first-run dashboard**: a new user types a join code, presses Join, and — right or wrong code — the screen does nothing.

**Fix:** render the toasts. Add a fixed viewport with `role="status" aria-live="polite"` (and `role="alert"` for errors), success/error/info variants, dismiss-on-click, and a stack cap. Position it so it does not collide with the notification popups (P1-20) — bottom-left is free; top-right is not.

### P0-2. A user invited to an organization cannot accept the invitation

**Where:** [OrgDashboardClient.tsx:88](src/components/orgs/OrgDashboardClient.tsx#L88)

```tsx
if (!items.length) {
  return <div className="surface-card p-6"><div>{tOrg("noOrgs")}</div></div>;
}
// ...pending-invitations block lives BELOW this return
```

The "you have no organizations" early return fires **before** the pending-invitations block renders.

**Impact:** the exact user who most needs `/orgs` — someone invited to their first organization — sees "You have no organizations" and no way forward. The invite is fetched, polled every 30s, and never shown. This is a complete funnel stop for team adoption.

**Fix:** render pending invites above the empty state and never gate them on `items.length`. While there, give the empty state real CTAs — "Create an organization" and "Join with a code" — instead of a sentence (see P1-31).

### P0-3. The command palette ships three destinations that 404

**Where:** [CommandPalette.tsx:68–71, 78](src/components/layout/CommandPalette.tsx#L68)

| Palette row | `href` | Route exists? |
|---|---|---|
| Tasks | `/tasks` | **No** |
| Events | `/events` | **No** — events live at `/publish` |
| *every project row* | `/projects/{id}` | **No** — there is no project detail route |
| Settings | `/settings` | Yes (defaults to `profile`) |

Same dead link at [ConversationDetails.tsx:158](src/components/chat/ConversationDetails.tsx#L158) — the "open project" link from a chat's details panel.

**Impact:** the palette's stated purpose is "type what you want and go there". Two of its eight static rows and *all* of its dynamic rows land on the 404 page. A user who tries it once will not try it twice.

**Fix:** point Tasks and Events at the routes that exist (`/create`, `/publish`) or — better — create the routes (P1-9, P1-10). Until a project detail route exists, project rows must use the same href the projects list uses.

### P0-4. The note-password reset email leads to a dead end, and can lock a user out of their own encrypted note permanently

**Where:** [reset-password/page.tsx](<src/app/(auth)/reset-password/page.tsx>), [email.ts:302](src/server/email/email.ts#L302), [note.ts:653](src/server/api/routers/note.ts#L653)

Four compounding problems:

1. The email builds `/reset-password?noteId=…&token=…`. **The page never reads `token`.** It asks for a numeric recovery PIN instead.
2. `note.resetPasswordWithPin` throws `BAD_REQUEST: "No reset PIN configured"` if the user never set one. Nothing in the note-locking flow asks them to (P1-21). Since content is AES-256-GCM under a key derived from the password, a forgotten password with no PIN is **permanent data loss**.
3. `/reset-password` is in `PUBLIC_PATHS` but calls a `protectedProcedure` — an unauthenticated visitor following the email link gets a raw `UNAUTHORIZED` error, not a sign-in prompt.
4. On success it redirects to `/create?action=new_note` — the **deprecated** notes surface — rather than to `/notes/{noteId}`, the note the user just unlocked.

**Impact:** the recovery path for encrypted notes does not work. Worse, the route name promises account password reset (which actually lives inside `SignInModal`), so users arrive here with the wrong expectation.

**Fix:** rename the route to `/notes/{noteId}/recover`; honour the emailed token as the credential; require a session or show the sign-in modal with `callbackUrl`; redirect to the unlocked note; and localize the page.

### P0-5. The event Share button copies a link that does not work

**Where:** [EventFeed.tsx:523](src/components/events/EventFeed.tsx#L523)

```ts
const eventUrl = `${window.location.origin}/publish?event=${event.id}`;
```

Nothing reads `?event=`. `useSearchParams` does not appear in `publish/page.tsx` or in any `components/events/*` file. And `/publish` is **not** in `PUBLIC_PATHS`, so the recipient is bounced to the landing page first.

**Impact:** sharing an event — the core distribution action for an events product — produces a link that requires sign-in and then lands on the top of an unfiltered feed. The README promises "public event pages with images and details". There is no event route at all, so no event is addressable, indexable, or shareable.

**Fix:** add a real public route (`/events/[id]`) with its own metadata and Open Graph tags, add it to `PUBLIC_PATHS`, and share that. As an interim, have `/publish` read `?event=` and scroll to + highlight the card.

### P0-6. Most new users never see onboarding

**Where:** [OnboardingGate.tsx](src/components/auth/OnboardingGate.tsx) — mounted only in `create/page.tsx`, `notes/page.tsx`, `notes/new/page.tsx`, `notes/[noteId]/page.tsx`.

Sign-in redirects to `/dashboard` ([app/page.tsx](src/app/page.tsx)). The dashboard has no gate. So the workspace-shape decision — organization vs. personal, which drives roles, visibility and the whole data model — is silently skipped for anyone who does not wander into Notes or Create.

Two further problems in the gate itself:
- `if (isLoading) return <>{children}</>` — the dashboard paints first, then the modal slams over it.
- `dismissed` is local state, so the gate re-arms on every navigation until the mutation lands.

**Impact:** a brand-new user lands on a first-run dashboard with no role, no workspace, and no guidance about what KAIROS is for. Their `usageMode` stays unset indefinitely.

**Fix:** move the check to a shared `(app)` layout (P1-15) or the dashboard itself, render nothing (not `children`) while loading, and add the missing third option below.

### P0-7. Project chat is fully implemented on the server and unreachable in the UI

**Where:** [ProjectChat.tsx](src/components/projects/ProjectChat.tsx) — 14 KB, zero importers.

| Procedure | Only caller |
|---|---|
| `chat.getOrCreateProjectConversation` | `ProjectChat.tsx` (orphaned) |
| `chat.listProjectConversations` | `ProjectChat.tsx` (orphaned) |
| `chat.listProjectUsers` | `ProjectChat.tsx` (orphaned) |

The new chat surface (`ChatShell` → `NewChatModal`) is **1:1 DM only** — project members appear as *suggestions* for a direct message, never as a group. There is no way to create any group conversation.

**Impact:** README promises "Teams — project-level collaborators, **real-time chat** and timelines against the same project" and "Direct messages **and project chat**". Half of that is invisible. Team coordination — arguably the product's reason to exist — has no group surface.

**Fix:** add a "Project" section to `ConversationRail` backed by `listProjectConversations`, and a group option in `NewChatModal`. Then delete `ProjectChat.tsx`.

### P0-8. The AI's undo window has no interface

**Where:** [agent.ts:893–908](src/server/api/routers/agent.ts#L893) — `undoAvailability`, `undoApply`. Zero callers in `src/components`.

**Impact:** the README's central trust claim for the agent suite is "an undo window on applied plans". Four of the five agents write real data. A user who lets A2 generate a 20-task backlog or A3 rewrite a note has no way to take it back from the UI — the safety net exists but is not wired to anything. This directly undermines the draft → confirm → apply promise that makes the AI layer feel safe to use.

**Fix:** after any apply, show a persistent "Applied — Undo" affordance in the chat turn for as long as `undoAvailability` reports a window, with a countdown. This is the single highest-trust-per-line-of-code change available in the AI surface.

## P1 — Major friction, missing core, or wrong mental model

### Information architecture

**P1-9. There is no project detail page.** [ProjectsWorkspace.tsx:51](src/components/projects/ProjectsWorkspace.tsx#L51) says it plainly:

```ts
/** Tasks and the board still live behind the create flow. */
const projectHref = (id: number) => `/create?action=new_project&projectId=${id}`;
```

Opening a project navigates to a URL that says *create a new project*. There is no `/projects/[id]`. Consequences: the URL lies; you cannot share a link to a project; the palette and chat both have to link somewhere that 404s (P0-3); and the browser back button behaves unpredictably because project, task board and timeline are all the same route with different query params.

**Fix:** create `/projects/[projectId]` (with `/tasks`, `/timeline` sub-tabs if useful) and reduce `/create` to actual creation.

**P1-10. `/create` does not create, and notes have two different UIs.** The nav item labelled **Create** with no `action` param renders `TaskTimelineClient` — a task timeline. `?action=new_note` renders the **old** `NotesList` (32 KB) beside `CreateNoteForm`, while `/notes` renders the entirely different new `NotesWorkspace`. Two notes experiences with different capabilities, layouts and interaction models are both reachable and both linked from the app.

**Fix:** retire `?action=new_note` and redirect it to `/notes/new`; delete `NotesList.tsx`; rename the nav item to match what the page shows, or make the page a create surface.

**P1-11. There is no workspace search.** README: "Full-text search across the workspace". Reality: `scripts/sql/search-indexes.sql` is a **zero-byte file**; there is no search procedure in the `note`, `task`, `event` or `project` routers. The only search in the product is per-list client-side filtering, chat message search, and user-email lookup. A user cannot find a note by its content, a task by its title, or an event by name from anywhere.

**P1-12. ⌘K is invisible.** The command palette is genuinely well designed (local matching, explicit AI fallback, accent-insensitive), and **nothing in the UI mentions it** — no search field in the TopBar, no hint, no menu entry, no shortcut list. There is no visible search affordance anywhere in the application.

**Fix:** put a real search input in the TopBar that opens the palette on focus, with `⌘K` rendered in it. This solves P1-12 and gives P1-11 a home.

### Authentication and session

**P1-13. Unverified accounts are a permanent dead end.** [SignInModal.tsx:151](src/components/auth/SignInModal.tsx#L151) collapses every failure to `t("signIn.invalidCredentials")`. But credentials sign-in is also refused for **unverified email** and blocked by **login lockout**. The "resend verification" control exists only on the `verifyEmailSent` view, reachable solely in the seconds after signup. A user who signs up, misses the email, and returns tomorrow is told their password is wrong, forever, with no path out.

**Fix:** distinguish the cases. On `EMAIL_UNVERIFIED`, show "Confirm your email" + a resend button. On lockout, say how long. Keep the generic message only for genuine credential mismatches.

**P1-14. Session expiry drops the user on marketing copy with no explanation.** Every app page does `redirect("/api/auth/signin")`, and `pages.signIn` is `/` — so the `callbackUrl` is discarded. (`notes/*` redirect to `/` directly, also without it.) The proxy handles the common case correctly, but when a *stale* cookie is present the page-level redirect fires: the user is silently dumped on the landing page, sign-in modal closed, destination lost, with no "your session expired".

**Fix:** replace every page-level `redirect("/api/auth/signin")` with `redirect("/?callbackUrl=" + encodeURIComponent(pathname) + "&reason=expired")` and have `HomeClient` show a note. Better: do the check once in a shared `(app)` layout.

### The shell

**P1-15. There is no `(app)/layout.tsx`, and it costs a lot.** All 15 app pages hand-roll `<SideNav />` + `<TopBar />` + `rail-offset`. Consequences:

- **The whole shell remounts on every navigation.** `SideNav` reads its pin state from `localStorage` in a `useEffect`, so pinned users see `--rail-w` snap 4rem → 14.75rem and the page content jump sideways on *every* page load. The pre-paint script in [themeInitScript.ts](src/server/http/themeInitScript.ts) handles theme and accent but not the rail.
- **The TopBar is missing on 6 of 15 pages** — `notes` (×3) and `chat` (×3). Nothing replaces it, so on Notes and Chat there is **no notification bell, no workspace switcher, no user menu and no sign-out**. The user must navigate away to see whether anything happened.
- Onboarding, auth checks and error boundaries are duplicated or absent per page. There is no `(app)/error.tsx`, so any app error escapes to the global one and the user loses the entire navigation.

**Fix:** one `(app)/layout.tsx` holding the auth check, `SideNav`, `TopBar` (with a slot for page actions), `OnboardingGate` and an `error.tsx`. Add `railPinned` to the pre-paint script.

### Mobile

**P1-16. The mobile bottom bar hides the primary destinations.** [SideNav.tsx:130](src/components/layout/SideNav.tsx#L130) — the bottom bar is Events · Progress · **New** · Calendar · Settings. Dashboard, Projects, Chat and Notes — four of the five most-used destinations — are only in the hamburger drawer. All bottom-bar items are icon-only with `title` (which does nothing on touch) and no visible label.

**P1-17. The Ask Kairos launcher sits on top of the mobile bottom bar.** [AskKairosLauncher.tsx:41](src/components/chat/AskKairosLauncher.tsx#L41) is `fixed right-4 bottom-4 z-40`; the bottom nav is `fixed bottom-0 … z-40`. Same stacking level, and the launcher renders later in the tree so it wins — covering the rightmost nav items (Settings, Calendar) on every phone.

**Fix:** `bottom-24 lg:bottom-6` on the launcher, and raise the nav's z-index.

**P1-18. Mobile users cannot filter events by region at all.** [publish/page.tsx](<src/app/(app)/publish/page.tsx>) puts the region `<select>` inside `FeedLeftSidebar`, which is `hidden lg:block`, *and* passes `hideRegionFilter={true}` to `EventFeed`. Below 1024px there is no region control on the page. For a product whose event model is built around Bulgarian regions, the primary discovery filter is desktop-only.

**P1-19. The core project and task surfaces are effectively desktop-only.**

| File | Lines | Responsive utilities |
|---|---|---|
| `ProjectManagement.tsx` | 786 | **0** |
| `InteractiveTimeline.tsx` | 763 | 2 |
| `MilestoneTimeline.tsx` | 641 | 2 |
| `TaskTimelineClient.tsx` | 1,734 | 19 |
| *(for contrast)* `ProjectsWorkspace.tsx` | 971 | 20 |

`ProjectManagement` is the project workspace + collaborator manager and has **not one breakpoint**. These are the surfaces where a user actually manages work; on a phone they overflow.

### Notifications

**P1-20. The notification centre has six separate problems.** [NotificationSystem.tsx](src/components/notifications/NotificationSystem.tsx)

1. **Entirely unlocalized.** "Notifications", "unread", "Clear All", "Clearing…", "No notifications", "You are all caught up!", "Click to view →", and both `aria-label`s are hardcoded English. This is the one component visible on nearly every page, in a Bulgarian-first product with complete `bg` coverage everywhere else.
2. **"Clear All" permanently deletes every notification on one click** — no confirmation, no undo, no "are you sure".
3. **Per-item delete is unreachable on touch.** The X is `opacity-0 group-hover:opacity-100` — there is no hover on a phone, and no `focus-visible:opacity-100` for keyboard.
4. **No "mark all as read".** And clicking a notification to mark it read *also navigates away* — so there is no way to clear the badge without leaving the page, 50 times.
5. **The floating popup stack is unbounded** (`setFloatingNotifs(prev => [...prev, notif])`). A burst of activity stacks cards down the screen from `top-4 right-4`, over the TopBar.
6. **No keyboard or a11y story:** Escape does not close the dropdown, focus is not managed, and the bell has no `aria-expanded` / `aria-haspopup`. Relative times use bare `formatDistanceToNow` instead of the project's own `useDateFormat` hook, so they stay English.

### Data loss and trust

**P1-21. Locking a note never warns that the content is unrecoverable.** The entire copy at lock time is `notes.password.protect` = "Protect with a password". There is no mention that content is encrypted under that password, that KAIROS cannot recover it, or that a recovery PIN should be set first — and the PIN lives in an unrelated place (Settings → Security). Combined with P0-4, a user can permanently destroy their own data by forgetting a password they were never told mattered.

**Fix:** at lock time, state plainly that the note cannot be recovered without the password, and offer to set the recovery PIN inline if none exists.

**P1-22. Visiting the landing page permanently flips a light-mode user to dark.** [HomeClient.tsx:39](src/components/homepage/HomeClient.tsx#L39):

```ts
useEffect(() => { setTheme("dark"); }, [setTheme]);
```

`next-themes` `setTheme` **writes to localStorage**. So any visit to `/` — including landing there after sign-out, since `signOut({ callbackUrl: "/" })` — overwrites the user's saved theme. On the next sign-in the pre-paint script paints dark, then `UserPreferencesProvider` fetches the server preference and flips to light: a visible flash *and* a preference the user has to keep re-setting.

**Fix:** scope dark to the landing page with a `dark` class on its own root (it already sets `className="dark"`), and never call `setTheme`.

**P1-23. The accent colour flashes purple in every new tab.** [themeInitScript.ts:35](src/server/http/themeInitScript.ts#L35) reads `sessionStorage.getItem('user-accent')`, and [UserPreferencesProvider.tsx:74](src/components/providers/UserPreferencesProvider.tsx#L74) writes it there. `sessionStorage` is per-tab, so every new tab and every fresh session paints the default purple, then corrects to the user's real accent after the settings query resolves. It should be `localStorage` — the value is a durable preference, not session state. (`UserPreferencesProvider` also carries a no-op effect at lines 49–56 that reads a variable and returns.)

**P1-24. The landing intro curtain replays on every single load.** `themeInitScript` sets `dataset.kairosIntro = 'play'` unconditionally; the only opt-out is `prefers-reduced-motion`. A returning visitor — or anyone who just signed out — watches the full intro animation again, every time.

**Fix:** stamp `'seen'` in `localStorage` after the first play.

**P1-25. Deleting a task can fail silently.** [TaskTimelineClient.tsx:1348](src/components/progress/TaskTimelineClient.tsx#L1348) — the only `onError` in the codebase with no user-facing branch:

```ts
onError: (err) => { setDeletingId(null); console.error("[TaskDelete]", err.message); },
```

The row simply reappears with no explanation. (Every other mutation at least *calls* `toast` — which, per P0-1, is also invisible, but that is one fix rather than two.)

### Consistency

**P1-26. Four different patterns for confirming a destructive action.**

| Pattern | Where |
|---|---|
| Native `confirm()` | `WorkspaceSettingsClient` — **leave organization**, **remove member**, **delete role** |
| Custom accessible modal | `notes/ConfirmDialog`, `chat/ConfirmDialog` |
| Two-click "arm" with a 4s timeout | `EventFeed` — delete event |
| Inline confirm/cancel button swap | `TaskTimelineClient` — delete task |
| Overlay with `role="dialog"` | `ProjectsWorkspace` — delete project |

The three highest-stakes actions in the product use the unstyled, unthemed, un-dismissable native dialog. The 4-second arming window in `EventFeed` is its own hazard: the confirmation silently disarms while the user is reading it.

**Fix:** promote `notes/ConfirmDialog` to `components/ui/ConfirmDialog` and route all five through it.

**P1-27. The two most important modals in the product are inaccessible.**

| Component | `role="dialog"` | `aria-modal` | Escape | Focus trap / restore |
|---|---|---|---|---|
| **`SignInModal`** (the front door) | ✗ | ✗ | ✗ | ✗ |
| **`RoleSelectionModal`** (onboarding) | ✗ | ✗ | ✗ | ✗ |
| `EventFeed` create/edit event | ✗ | ✗ | ✗ | ✗ |
| `TaskTimelineClient`, `MilestoneTimeline` | ✗ | ✗ | ✗ | ✗ |
| `NotesList` (old) | ✗ | ✗ | ✗ | ✗ |
| `notes/*`, `chat/*`, `CalendarDrawer`, `NewProjectDrawer`, `CommandPalette` | ✓ | ✓ | ✓ | ✓ |

The newer surfaces do this properly, including `document.activeElement` restore and Tab cycling. The oldest — and the two a *first-time* user must get through — do none of it. `RoleSelectionModal` additionally has no close button at all, so a keyboard user who cannot operate it is stuck.

**P1-28. No modal locks background scroll.** No `document.body.style.overflow` handling anywhere. Every overlay in the app lets the page scroll behind it — particularly bad on iOS.

**P1-29. Onboarding offers no way to join an existing organization.** `RoleSelectionModal` offers *Create an organization* or *Personal*. The join-with-a-code input exists only on the first-run **dashboard** — which the gate blocks. So an invited user's only options are to create a redundant organization or pick Personal and hunt for the join flow later. (README also names an "individual" role that is never offered.)

**P1-30. The workspace menu dead-ends when you have no organizations.** [WorkspaceMenu.tsx:207](src/components/orgs/WorkspaceMenu.tsx#L207) renders `t("noOrgs")` with no "Create" or "Join" action. Creating a second organization is possible only through Settings → Workspace or the orphaned `OrgSwitcher`; it is not offered where the user is actually thinking about workspaces.

**P1-31. The skip link is broken on four routes.** `<a href="#main-content">` is in the root layout, but `settings/page.tsx` and all three `(auth)` pages have no element with that id. (`settings` has a `<main>` — it is just missing the id.)

**P1-32. An unrecognised `?section=` renders a blank settings page.** [settings/page.tsx](<src/app/(app)/settings/page.tsx>) is a chain of `activeSection === "…" && <Component />` with no fallback. A stale or mistyped link shows the nav and an empty panel. Section changes are also full `<Link>` navigations, so the whole shell re-renders on every settings tab click.

**P1-33. The AI budget is only visible in the floating widget.** `agent.rateLimitStatus` is rendered in `A1ChatWidgetOverlay` but not on `/chat/ai`, the dedicated AI console. On the page where a user is most likely to spend their quota, they cannot see it — and when it runs out, the failure arrives with no context.

**P1-34. Sign-up requires agreeing to terms that do not exist.** `staticPages.privacyBody` = *"Our privacy policy is being prepared and will be published here."* Same for `termsBody` and `securityBody`. The consent checkbox under the sign-up button links to all three.

**P1-35. No `Accept-Language` detection.** [i18n/config.ts](src/i18n/config.ts) reads only the `NEXT_LOCALE` cookie and falls back to `en`. A Bulgarian visitor's first impression of a Bulgarian-market product is in English, and the switcher exists only in the landing header and Settings.

**P1-36. Calendar state is not in the URL.** `view` and `anchor` are component state in `CalendarWorkspace`. A user cannot bookmark or share "week of 14 Sept", and the back button does not undo calendar navigation. There is also no drag-to-reschedule, and no keyboard arrow navigation between cells.

**P1-37. Calendar export is one-shot, and data export is buried.** `/api/export/ics` produces a file, not a subscribable URL, so an exported calendar is stale the moment a task moves. Both live under **Settings → Security**, next to Delete Account — a defensible pairing, but not where anyone looks for "export my calendar".

## P2 — Polish, consistency, hygiene

**P2-38. The collapsed rail is eight unlabelled icons with no tooltips.** `RailLink` renders labels at `opacity-0` inside `overflow-hidden` and sets no `title`. Unpinned (the default), a new user must hover the rail itself to learn what anything is; a single icon gives them nothing.

**P2-39. Remaining hardcoded English.** `"Kairos AI"` (twice in `SideNav`), `A1ChatWidgetOverlay` aria-labels ("Open full screen", "Close"), `"RSVPs"` and `"No event data yet."` in `publish/page.tsx`, `"Organization name…"` in `OrgSwitcher`, placeholders in `MemoryPanel`, `AiTaskPlannerPanel` and `ProjectIntelligenceChat`, plus the whole of `verify-email` and `reset-password`. Also the root `error.tsx`, `not-found.tsx` and `loading.tsx` — the pages a user sees precisely when something has gone wrong.

**P2-40. `/publish`'s "Event Progress" percentage is meaningless.** `(likes + comments) / max(likes + comments) × 100` — the top event is always 100%, and the number describes nothing a user can act on. The right sidebar also runs its own `getPublicEvents({ limit: 50 })` alongside the feed's paginated query: two requests, two sources of truth.

**P2-41. Menu semantics without menu keyboard behaviour.** `WorkspaceMenu` uses `role="menu"` / `role="menuitem"` but has no roving tabindex and no arrow-key handling — the ARIA contract promises behaviour the component does not implement. (`notes/Menu.tsx` and `NoteList.tsx` do it correctly and are the model to copy.)

**P2-42. Dead code shipped to users.** `ProjectsListWorkspace.tsx` (15 KB), `A1ChatFloating.tsx`, `ProjectChat.tsx` (14 KB), `ConversationsRail.tsx` (superseded by `ConversationRail`), `NotesList.tsx` (32 KB, superseded but still routed via `/create?action=new_note`).

**P2-43. `ProjectIntelligenceChat.tsx` is a single 105 KB client component.** It is the AI surface embedded across the app; at that size it is a meaningful first-load cost and effectively unreviewable.

**P2-44. Marketing and legal pages force `className="dark"`.** A light-mode user clicking Privacy from the footer gets a dark page.

**P2-45. Raw server messages reach the user.** Sign-up and several mutations surface `error.message` from tRPC verbatim. Once toasts are visible (P0-1), these become the app's error voice — worth a pass for tone and actionability.

## What is already good

Worth stating, because the fix list above is long and the recent work is genuinely strong:

- **Notes** is the best surface in the product. A note is a route, not state, so back/deep-link/share all behave. `useAutosave` is careful in ways most implementations are not: dirtiness measured against server state rather than a mutable ref, and pending edits *handed off* to the note they were typed into when you switch away. The save status is honest, including the "typed while in flight" case.
- **Chat** has focus traps with `activeElement` restore, `aria-live` on the thread and typing indicator, drafts, presence, and reactions/edit/pin/search all wired.
- **Accessibility fundamentals** are in place globally: `:focus-visible` rings on all interactive elements, a skip link, and `prefers-reduced-motion` honoured in **11** separate places in `globals.css` — including the rail transition.
- **i18n discipline is unusually honest.** `bg` has exact key parity with `en` (1,635/1,635), and `de`/`es`/`fr` are quarantined in `INCOMPLETE_LOCALES` with a test that blocks promotion until they reach parity — after someone noticed half-translated screens were being shipped.
- **The export route replaced a button that lied** ("you'll receive an email" that did nothing), and deliberately sits next to Delete Account so "take a copy" and "destroy it" are offered together.
- **QR invites are not burnt by a scan** — arriving at `/join/[code]` describes the invite; redeeming requires a press. The `callbackUrl` is carried across sign-in for exactly this case, and validated as same-site.
- **The CSP is real**, with the theme script allowed by hash rather than nonce and a test keeping the hash in step.
- The code comments throughout the newer tier explain *why*, including several notes admitting a previous version was wrong. That is the habit that produced the good surfaces, and applying it to the older tier is most of this audit.
