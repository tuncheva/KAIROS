UI proposal · Pro features

Eleven capabilities, all reachable

Phases 0–3 of the Pro roadmap have shipped as server code and the schema is migrated: entitlements, timezone-correct scheduling, a weekly retrospective, standing rules, export, history retention and search, deadline watch, email delivery, saved schedules, per-plan ceilings, field-level plan diffs, a real undo, API keys, webhooks and document search. All of it is tested. Five of those features have no way in at all — and one of them, undo, has had none since before this work began.

Update: all of it is now built. This document is kept as the record of where each one lives and why. Where the implementation diverged from a mockup below, the section says so.

It proposes where each one lives, what it looks like, and the order it was built in. It is deliberately conservative about new surfaces: a capability nobody can find is indistinguishable from one that does not exist, and the cheapest fix is almost always an existing page rather than a new one.

01 · The one that changes behaviour

The plan diff, inside the confirm card

Every agent write goes through draft → confirm → apply. Today the confirm step says 3 creates · 2 updates and offers a button. That is a count, not a review, and the honest expectation is that most people press Apply without reading — which is exactly what undo.ts says undo exists to make safe.

agent.taskPlanDiff returns the field-level change set. Showing it turns the confirm card from an announcement into something a person can check. This is the highest-value item here: the only one that changes what a user understands before touching their data.

Chat · confirm card
I can reschedule the two overdue tasks in Delta and add the migration plan you mentioned.
edit Ship the invoice export
due date4 Sep 2026→18 Sep 2026
prioritymedium→high
edit Rewrite the onboarding copy
statuspending→completed
create Draft the Q4 migration plan
projectDelta
1 task in this plan no longer exists and will be skipped.
Undoable for 10 minutes after applying

Design notes. Fields that would not change are omitted — the API already drops them, because a plan patch routinely restates values at their current setting and a diff full of no-ops is one nobody finishes reading. Creates show no before/after because there is no prior row. The undo window is stated before the click, since that is when it affects the decision.

The amber line is not decoration. taskPlanDiff returns a missing array: tasks the plan names that no longer exist, because a colleague deleted one in the two minutes since the draft was written. Without that line the card promises more than the apply will do.

02 · The oldest gap

Undo, where the apply happened

Undo now performs a real rollback: creates are deleted and edits are restored from the before-image. Deletes are still not reversible — the row is gone and re-inserting it would take a new id, orphaning every comment and activity entry that pointed at the old one. The API reports which is which, so the UI must show a partial outcome rather than a single cheerful toast.

After apply
Applied — 3 changes
2 tasks edited, 1 created · in Delta
Undo available for 9 more minutes
After a partial undo
Partly undone
Restored 2 edited tasks and removed 1 created task. 1 deleted task could not be restored — its contents are recorded, but re-creating it would break anything that referred to it.

Why the second state matters. UndoResult.notReversed is an array of sentences written for exactly this panel. Collapsing it into “Undone” would tell someone their data is back when part of it is not — the worst thing this feature could do.

03 · Settings → AI

Saved schedules

The Daily Brief and Risk Radar are two fixed questions on a timer. Saved schedules make that an open surface: every Monday, list the unassigned tasks in Delta. The runner, the cap, the read-only tool binding and the CRUD all exist. What is missing is a form.

It belongs under the existing proactive card rather than in its own section — a user who has just set their brief to 07:00 is in exactly the frame of mind to add a question of their own, and splitting the two would make the built-ins look like a different feature.

Settings → AI · proactive
Daily brief
One message each morning: what is due, what slipped, what is at risk.
Weekly retrospective
What closed, what carried over, what stopped moving.
Times are in Europe/Sofia, your profile time zone.

Your own schedules 2 of 3 used

Monday triage
“List the unassigned tasks in Delta and who could take them”
Stale review check
“Which tasks have been in review for more than five days?”

Two things the form must say. That a schedule can only read — it runs against the read-only tool set with the memory-writing tools withheld, and a user who expects “every Monday, assign the unassigned tasks” should learn that from the form and not from silence. And the allowance, as 2 of 3 used, so the cap is visible before it is hit rather than as a refusal.

04 · Chat → AI agents page

Documents, beside the conversation

Upload a spec or a contract and the agents can cite it. Decided: this lives in the chat on the AI agents page, not in settings — documents are what the agent reads, and the moment a user wants to add one is the moment they are asking a question the file would answer. Settings is where you go to change how the product behaves; this is content.

Concretely: a third tab on the right-hand rail that already holds the trail, tools and memory panels. Same shell, same width, no new route. The status states below are unchanged by the move — they are the real design problem either way.

Status is the whole design problem. A file can be indexing, ready, failed, or contain no text at all — and the last of those is not a failure. An image-only scan needs OCR, which is out of scope, and telling someone “failed” sends them to support instead of to a different file.

Chat → AI agents · right rail, Documents tab
Drop a PDF or text file
Up to 16 MB. Attach it to a project to share it with that team, or leave it personal.
Delta-master-agreement.pdf ready
Delta · 34 pages · 61 passages indexed
onboarding-spec.pdf ready
Personal · 12 pages · 28 passages indexed
scanned-invoice.pdf no text
This file has no text layer — it looks like a scan. It cannot be searched until it has been run through OCR.
Q4-plan.pdf failed
Storage returned 404

Retry appears only on failed. A no text row will produce the same outcome on every attempt, so offering Retry there invites a user to keep pressing a button that cannot help them.

The uncomfortable part. Retrieval is keyword search, not semantic — a decision taken deliberately, because embeddings cost inference per upload and the AI layer runs on free provider tiers. So how do I cancel will not find termination clause. The agent is told this and adapts its phrasing, but the documents tab should say it too, in one line under the uploader: “Search matches the words in your documents. Use the terms the document itself would use.” A user who does not know this concludes the feature is broken.

Developer — keys and webhooks

Two lists with one thing in common: both hand the user a secret exactly once, and both are unrecoverable afterwards. That single constraint drives the design of both panels.

Revoked keys stay listed. The row is kept deliberately — after a leak the first question is “was this key used, and when did we stop trusting it?”, and a deleted row cannot answer either half. Greyed, no actions, still visible.

The log is the point. Without it, the only answer to “why did my endpoint not fire?” lives in server logs the user cannot read. Showing attempts and the reason a 4xx was not retried turns a support ticket into something they can diagnose.

Also worth surfacing here: the signature scheme. A receiver has to verify HMAC-SHA256 over {timestamp}.{body}, and publishing that recipe next to the secret is the difference between a verified webhook and a header nobody checks. A short expandable block, not a link to docs that do not exist yet.

06 · Cheapest of the five

History search, in the conversations rail

Unlimited history is the Pro benefit; search is what makes it felt. Keeping every message earns nothing if the only route back to a decision from last quarter is scrolling — and the retention split means a Free user loses messages after 30 days, so this is the feature that makes the difference visible on day one rather than day thirty-one.

Chat · conversations rail
⚲ invoice export
Delta planning · 4 Aug
…we agreed to push the invoice export to the next sprint so the migration lands first…
Weekly triage · 22 Jul
…the invoice export is blocked on the finance API credentials…
Untitled · 3 Jun
…can you break the invoice export down into tasks with estimates…

Half a day of work. agent.searchMessages already returns the conversation id, title, matched content and timestamp. This is an input, a debounce and a list — and it is the highest ratio of felt value to effort on the page.

Sequencing

Build order, and why

Ordered by value per day rather than by phase. The first two items change whether a user trusts the agent with their data; the rest expose capabilities that are simply unreachable.

#ItemEst.Why here
1History search0.5dHighest value per day. Input, debounce, list — the API needs nothing.
2Plan diff in confirm card1.5dThe only item that changes what a user understands before writing to real data.
3Undo + partial-undo states1dPairs with the diff and closes a gap older than this whole roadmap.
4Saved schedules form1dAttaches to a card that already exists; no new route, no new IA.
5Documents rail tab2dThird tab on the AI page rail. Upload widget, four status states. No new route.
6Developer settings tab2.5dTwo lists, a show-once panel, a delivery log, and a Free-tier explainer. Most surface area.
7Copy pass0.5dFive locales. Every string above needs bg/de/es/fr.
Do 1–3 first even if the rest waits. Three days buys a confirm card a person can actually review, an undo that reports the truth, and a way back into your own history. Those three are the difference between a Pro tier that feels trustworthy and one that feels like a set of switches in a settings page.

Open questions

Decisions this proposal does not make

  • Resolved — where Documents belongs. The chat on the AI agents page, as a third tab on the existing right rail. Not a settings tab and not a top-level route: documents are content the agent reads, so they belong where the reading happens.
  • Does the diff replace the existing summary line, or sit under it? Under it reads better on a two-change plan and worse on a thirty-change one. A collapsed “show all 30 changes” may be right, but collapsing the thing the feature exists to show deserves a real decision rather than a default.
  • Resolved — Developer is visible. A settings tab, always shown. Every panel throws FORBIDDEN without apiAccess, so on Free it must explain the gate rather than erroring — the tab is a shopfront, not a trap.
  • Still true — not verified in a browser. Everything is built, typechecked, linted and covered by 2,165 passing tests, and the production build compiles. But both new surfaces need a signed-in session, so none of it has been seen rendering. That is the outstanding risk on this work.
  • One divergence worth knowing. The plan diff renders the authoritative change set from agent.taskPlanDiff, not the diffPreview strings the model already returns in its plan. The model writes sentences about its own plan and nothing checks them; the card reads the current rows and computes the difference. Both now appear in the confirm card — the model's prose above, the real diff below — which is more than the mockup showed and arguably one too many.
