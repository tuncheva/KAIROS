KAIROS · UI proposal · UX audit remediation

Thirteen surfaces
that need drawing

The UX audit lists 45 findings. Most are one-line edits with no design content — a wrong href, a sessionStorage that should be localStorage, a z-index collision. This document covers the remainder: the places where something has to be drawn before it can be built — twelve from the audit, plus one new feature (§13) requested on top of it. Every mockup uses the existing KAIROS tokens, unchanged — no new colours, no new type scale, no new radii. The point is that these surfaces should look like they were always there.

§ 01 — Wave 1 · P0-1

The app learns to speak

ToastProvider already has a correct ToastManager — TTL timers, dismiss, cleanup on unmount. It destructures the state value away and renders no viewport, so 126 calls across 23 files produce nothing. This is the whole design: a stack in the one free corner.

Bottom-left by default — but read from a token, not a hardcoded class. Top-right belongs to the floating notification stack (P1-20-5) and bottom-right to AskKairosLauncher, which leaves exactly one free corner today. §13 turns that into a user preference, so the viewport should take its anchor from a CSS custom property from the first commit rather than being retrofitted later. On mobile the stack lifts to bottom-24 so it clears the nav — the same offset the launcher needs in §9.

Rules the viewport has to follow

  • Two live regions, not one. role="status" aria-live="polite" carries success and info; role="alert" aria-live="assertive" carries errors. A save confirmation must not interrupt a screen reader mid-sentence; a failure must.
  • Capped at three. The unbounded stack is exactly the bug P1-20-5 documents in the notification popups. Do not ship the same defect twice in one release.
  • Errors persist longer. 3 s for success, 6 s for errors, and errors do not auto-dismiss while the tab is hidden.
  • Dismissible by pointer and by key. Click anywhere on the toast, plus an explicit × with a focus-visible ring.
  • Left rule as the variant carrier. A 2 px inset border in mint / strawberry / sky, so the kind survives a greyscale screenshot and does not depend on the icon alone.
  • Neutral elevation, no coloured halo. The toast sits on --shadow-pop like every other floating surface. Accent-coloured drop shadows are coming off buttons across the app — see the closing note.

§ 03 — Wave 2 · P0-5

An event you can actually send someone

Share currently copies /publish?event={id}. Nothing reads ?event=, and /publish is not in PUBLIC_PATHS, so the recipient signs in and lands on the top of an unfiltered feed. For an events product this is the core distribution action, and no event in KAIROS is addressable, indexable or shareable today.

§ 04 — Wave 2 · P0-6 · P1-29

Onboarding, with the option people actually need

The gate is mounted on /create and /notes/*. Sign-in lands on /dashboard. So the workspace-shape decision — the one that drives roles, visibility and the entire data model — is skipped for anyone who does not wander into Notes. And when it does appear it offers two doors, neither of which is join the team that just invited me.

Three doors, a close button, and a shortcut when the answer is already known. If the user has a pending invite, the modal says so and the join card becomes a one-click accept. The close button matters: RoleSelectionModal has none today, so a keyboard user who cannot operate it is trapped (P1-27).

Three behaviour fixes that ship with it

  • Mounted in (app)/layout.tsx, so every route is gated — not just the two that happen to import it.
  • return null while loading, not return children. Today the dashboard paints and the modal then slams over the top of it.
  • dismissed lifts out of local state. As component state the gate re-arms on every navigation until the mutation lands.

§ 06 — Wave 4 · P0-8

The undo window nobody can reach

agent.undoAvailability and agent.undoApply exist and work. Their only appearances outside the router are two boolean flags in entitlements.ts. Zero callers in src/components. This is the README's central trust claim for the agent suite, and four of the five agents write real data — a user who lets A2 generate a twenty-task backlog has no way to take it back.

§ 07 — Wave 4 · P0-4 · P1-21

Then resetPasswordWithPin throws "No reset PIN configured". A user can permanently destroy their own data by forgetting a password they were never told mattered.

§ 11 — Wave 6 · P1-20

The notification centre, six defects at once

It is the one component visible on nearly every page, and it is entirely unlocalized in a Bulgarian-first product with exact bg parity everywhere else. Clear All permanently deletes everything on one click. Per-item delete is opacity-0 group-hover:opacity-100, so it does not exist on touch. There is no mark-all-as-read, and clicking an item to read it also navigates away — so the badge cannot be cleared without leaving the page, fifty times.

§ 13 — Wave 6+ · NEW-1 · new scope

Where notifications appear, as a choice

Not an audit finding — a feature on top of the remediation. settings.notifications already exists with five toggles, and every one of them answers what to notify about. This is the first control for where. It sits in the same panel, as a second group above them.

The decision this forces

KAIROS has two on-screen surfaces: the toast viewport (§1) and the floating notification popups (P1-20-5). §1 puts toasts bottom-left because top-right and bottom-right were already taken. The moment position becomes user-chosen, that reasoning collapses — both surfaces cannot own the corner the user picked.

One preference, not two. The picker positions the notification popups; the toast stack automatically takes the diagonally opposite corner. One decision for the user, and a collision becomes structurally impossible. Two independent pickers would re-create the exact overlap this plan is fixing in §9.

What ships with it

  • One column, one enum. notificationPosition on users, defaulting to top-right — today’s behaviour, so no existing user sees a change until they ask for one. updateNotifications already spreads its input into the update, so the Zod schema is the only router edit.
  • CSS custom properties, not conditional class strings. --notif-anchor-* is set once on the document root and the toast viewport derives its own anchor by inverting it. Two components reading one token beats two components each holding a position switch.
  • Pre-painted. The value joins railPinned and the accent in themeInitScript (plan §3.2), so a toast firing early does not appear in the default corner and jump. Same CSP-hash bump, ideally the same commit.
  • Direction follows the edge. Anchored top, a toast slides down; anchored bottom, up — and both are suppressed under prefers-reduced-motion.
  • Six labels into en and bg together, like every other string this plan adds.

Delivery

What order, and what shares what

These twelve surfaces are not independent. Four shared pieces carry most of them, and building those first is what keeps the total near two weeks rather than four.

Built once, used everywhere

  • components/ui/Modal.tsx — dialog role, aria-modal, Escape, focus trap, activeElement restore, body-scroll lock. Extracted from the newer surfaces that already do it correctly. Used by §4, §7, §9, §12 and the six retrofits in P1-27.
  • components/ui/ConfirmDialog.tsx — §12, and the five call sites that currently roll their own, plus §11's Clear All.
  • (app)/layout.tsx — one shell. §4 mounts inside it, §8 and §10 depend on the TopBar it provides, and the six pages currently missing a TopBar get one for free.
  • OrgEmptyState — §2, and WorkspaceMenu's dead end (P1-30), and the join card in §4.

A note on the design system

Nothing in this document introduces a token. Every colour is --accent, --mint, --caramel, --straw, --sky or a foreground/border step already in globals.css; every radius and mono label matches the notes and chat surfaces shipped in 9535b5f. The audit's finding is that KAIROS reads as three generations of UI stacked on each other. Thirteen new surfaces are thirteen chances to make that worse — so they are drawn from the newest tier's vocabulary, deliberately, and the older tier moves toward them rather than the other way round.

One thing does change: the glow comes off. No button in this document carries a coloured drop shadow. The app currently has 41 uses of shadow-accent, plus shadow-accent-primary/20–30, ad-hoc shadow-[0_0_15px_rgb(var(--accent-primary)/0.3)], and .purple-glow / .purple-glow-soft / .progress-bar-glow in globals.css. A primary button is already identified by its accent fill — the halo carries no information, and it is the strongest single tell between the older tier and the newer one. Depth stays where depth does real work: neutral elevation on cards, modals, popovers and the toast viewport. :focus-visible rings are untouched, because those are an accessibility affordance rather than decoration. The cheapest route is to redefine --shadow-accent as a neutral elevation shadow first, so all 41 call sites move in one reviewable edit, and retire the class afterwards.
