KAIROS · Design proposal · /notes

Notes, rebuilt around
the act of writing

The vault underneath is the strong part — Argon2 hashes, AES-256-GCM content, ciphertext that never leaves the server unlocked, a PIN recovery path. What sits on top is a card grid that opens each note in a 512-pixel modal with a Save button. This proposal leaves the cryptography untouched, replaces the shell with a three-pane workspace built from the existing KAIROS tokens, and closes the gaps between what /notes is today and somewhere people would actually keep their thinking.

Where it stands

A good vault behind a bad desk

Reading NotesDashboard.tsx and note.ts end to end, the security work is the most careful code on the surface — and it is commented like someone had already been burned once. The problem is everything around it: one component holds thirty-plus useState hooks and four nested modals, the entire note corpus ships to the browser on load, and the writing surface is a <textarea> inside a dialog you have to dismiss before you can see anything else.

Already solid keep

  • Encryption that holds its line. getAll nulls content for protected notes and strips passwordHash / passwordSalt on both branches, so the endpoint cannot leak credential material whichever path it takes. getSharedWithMe strips the owner's hash too.
  • Re-encryption on save. The unlock password is deliberately held in memory so an edit can re-encrypt with it — the server refuses to write a protected note without one rather than quietly storing plaintext.
  • Recovery without a backdoor. Two failed unlocks surface the PIN reset path, and resetPasswordWithPin is the only route back in.
  • Unlock lifetime is the user's choice. notesKeepUnlockedUntilClose decides whether the in-memory unlock map survives navigation. Right default, right place.
  • Sharing has real permissions. note_shares carries read/write per person, update re-checks it server-side, and the share modal suggests org members instead of demanding an exact email.

What the shell gets wrong replace

  • Writing happens in a dialog. Opening a note mounts a max-w-lg, max-h-[80vh] modal over a 70% black scrim. You cannot see another note while writing, the textarea is min-h-[200px] and resize-none, and saving closes the note and refetches the whole list.
  • Nothing autosaves. Edits live in editingContent / editingTitle maps until you press Save. Clicking the scrim throws them away without a word.
  • The whole corpus loads at once. getAll returns every note with full content, unpaginated, and search filters that array in the browser. Fine at twenty notes, not at two thousand.
  • Tokens get bypassed. Cards are hardcoded dark:bg-[#1f1b2e] bg-[#efedf4], and nearly every border in the surface is border-white/[0.06] — white at 6% opacity, effectively invisible on a light background. The system already ships --hair and bg-bg-elevated for exactly this.
  • Two note surfaces exist. /create renders CreateNoteForm and NotesList — a second, older notes UI totalling 972 lines that duplicates create, unlock and edit against the same router.
  • Structure has nowhere to live. No tags, no pinning, no archive, no trash, no sort control, no colour. Notebooks are the only organising tool, and a note belongs to at most one.
  • Half the router is unreachable. updateNotebook has no caller, so a notebook can never be renamed and its description column can never be filled. calendarDate can be set at creation and never seen or changed again.

Worth fixing before anything visual

A locked note that is shared never shows that it is locked. The card badge is a ternary chain testing shareStatus !== "private" first, so the Shared chip wins and the lock chip is unreachable. The two states are orthogonal; both need to render.

Deleting a notebook asks with window.confirm. Deleting a note uses the styled dialog three hundred lines above it. Same surface, two confirmation languages — and the native one is the destructive path that also detaches every note inside it.

share_status duplicates note_shares. The enum on the note (private / shared_read / shared_write) restates what the shares table already knows per person, and nothing keeps the two in step when a share is revoked.

Direction

Rail, list, page — no modal in the writing path

The same three-pane spine the chat rebuild uses, tuned for documents instead of messages. A library rail holds the ways in — smart views, notebooks, tags. A note list is the current query made visible, with sort and filter where you can see them. The page is a real writing surface: full height, autosaving, wide enough to read a paragraph at a measure that doesn't fight you.

Modals survive only for things that are genuinely interruptive and reversible-or-not: sharing, deletion, PIN reset. Unlocking moves into the page as a gate — the note is selected, the list stays visible, and the password field replaces the body rather than the screen. Every colour, radius and shadow below is a KAIROS token; nothing new is invented.

The locked state

Unlocking is a gate, not an interruption

Today a locked note opens the same modal as any other and puts a password field where the text would be — with the rest of the app blacked out behind it. The mechanism is right; the framing is wrong. In the rebuild the note is simply selected: the rail and the list stay put, the page shows what it can (title, dates, who it is shared with) and asks for the password in place. Everything else about the flow — Argon2 verification, the attempt counter, the PIN reset after two failures, the in-memory unlock map — is unchanged.

Data model

Six columns and one join table

Unlike the chat rebuild, nothing here needs a structural rewrite — sticky_notes is shaped correctly, it is just thin. Most of the inventory above lands as nullable columns on the existing table, which means every change is additive and backfill-free.

Mobile

One pane at a time, and the rail comes back

Below 768px the current page hides the entire secondary sidebar, which is where notebooks, the tab switcher and the create button live — leaving a search field over a single-column card grid with no way to reach a notebook at all. The rebuild makes the panes routes: /notes is the list with the rail behind a sheet, /notes/[id] is the page, and Back is a real history pop rather than a state reset.

Delivery

Five phases, shippable in order

Ordered so the correctness and payload problems land before any pixels move, and so the redesign arrives after there is new state worth rendering. Phases 1 and 2 are safe to ship behind no flag at all; phase 3 is the one that wants a preview toggle.

01

Correctness & payload no visual change

Fix the badge ternary so lock and share states can coexist. Replace the window.confirm on notebook delete with the dialog already in the file, and say what happens to the notes inside. Add note.list with cursor pagination and a preview projection so the browser stops receiving every note body on load. Move the hardcoded card colours and border-white/[0.06] onto tokens — a one-file sweep that fixes light mode immediately.

02

Structure migration

Add pinned_at, archived_at, deleted_at, version, updated_by_id, the tag tables and the notebook columns. Ship pin, archive, trash/restore and sort against the existing UI. Wire updateNotebook. Retire share_status in favour of a derived field.

03

The redesign ui

Rebuild the shell as the three panes above. Split the 1394-line NotesDashboard into NotesRail, NoteList, NoteRow, NotePage, LockGate, ShareDialog and useAutosave; the password and unlock logic moves across unchanged. Route-driven /notes/[id], autosave with optimistic cache patches, skeletons and real empty states, keyboard navigation and focus management. Delete NotesList.tsx and CreateNoteForm.tsx once /create redirects here.

04

The writing surface content

Markdown rendering behind content_format, checklists, word count, calendar date editable after creation, notebook colours and ordering, tag management in the page footer, and setPassword / removePassword so a note can be locked after the fact.

05

Search & collaboration scale

The tsvector column, note.search with headline snippets, the ⌘K palette, then note:updated over the existing ws-server with version-based conflict warnings and viewer presence. Finally, surface the A3 Notes Vault draft/confirm pipeline as a review strip so the agent's proposed edits are approved where the notes actually live.

Open questions

Decisions this proposal doesn't make

  • Markdown, or stay plain? Nothing in package.json renders markdown today, and adding a renderer means an XSS surface on shared content. The proposal assumes a sanitised read-side renderer with a plain textarea for editing — no WYSIWYG dependency. Worth confirming that checklists are enough to justify it at all.
  • Autosave on encrypted notes. Every autosave of a protected note re-runs AES-GCM encryption server-side and rewrites the row. Acceptable at an 800ms debounce, but it does mean a locked note's updated_at moves while you type. Longer debounce for locked notes, or accept it?
  • What happens to notes when a notebook is deleted? The FK is set null, so they quietly become unfiled. Fine, provided the dialog says so — or should deletion offer to move them somewhere first?
  • Does /create survive? It is a second notes surface with its own 972 lines. This proposal assumes it redirects to /notes and both components are deleted, but it may be doing something for onboarding that is not obvious from the code.
  • Tags versus notebooks. Two organisers is one more than most people use. Tags are proposed because a note genuinely belongs to several contexts — but if notebooks become multi-assign instead, tags stop earning their tables.
  • Trash retention. Thirty days is assumed. Nothing prunes sticky_notes today, and a soft delete without a sweep is just a slower leak.
