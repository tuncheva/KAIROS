KAIROS · Design proposal · /chat

Chat, rebuilt as a
first-class surface

The transport layer is already good — optimistic sends, cursor pagination, Socket.IO rooms and typing indicators all work. What's missing is everything that tells a person what happened to their message. This proposal keeps the plumbing, replaces the shell, and closes the gaps between what /chat is today and a chat people can run a workday on.

Where it stands

What works, and what the shell hides

Reading ChatClient.tsx and chat.ts end to end, the real problem isn't code quality — several of the hardest parts are handled carefully, with comments explaining exactly why. The problem is that the UI exposes almost none of the state the system already knows about, and the data model stops one table short of a working chat.

Already solid keep

  • Optimistic sends that survive concurrency. Each send carries its own placeholder id through to onSuccess, so a second message sent mid-flight no longer erases the first one's placeholder.
  • Backwards pagination done right. prevCursor with fetchPreviousPage prepends history above the newest message, with scroll-anchor restoration on requestAnimationFrame.
  • Socket rooms that survive reconnects. The connect listener re-joins the conversation room after a network blip — without it, typing indicators died silently.
  • Duplicate-safe fan-out. The server pushes to the conversation room and each user room; hasMessage absorbs the double delivery.
  • Typing indicators with a sender ping interval, an idle stop, and a receive timeout tuned so an indicator neither flickers between pings nor hangs forever when a tab closes.

Structurally missing rebuild

  • No read state anywhere. No unread badge, no "seen", no new-messages divider, no way to mark a thread read. There is no column to store it in.
  • Attachments are string-concatenated into body and re-parsed on render with an image-extension regex. Nothing knows a file's name, size, or type, and prose containing a URL can trip the parser.
  • Deleting a conversation deletes it for both people. deleteConversation hard-drops the row and cascades every message — the other participant loses their history without consent or notice.
  • A notification row is written on every single message, even when the recipient is looking at the thread. An active conversation floods the bell.
  • The composer is an <input type="text">. The Enter / Shift+Enter handler exists, but Shift+Enter cannot insert a newline into an input — multi-line messages are impossible.
  • A failed send just vanishes behind a toast. No retry, no failed state on the bubble, and the typed text is already cleared.
  • Conversations are hard-wired to two people via userOneId / userTwoId. No group threads, and no room to add them without a migration.

Worth fixing before anything visual

Two of these are correctness issues, not polish: the destructive deleteConversation and the unconditional notification insert. Both ship today. They are phase 1 below, ahead of the redesign.

Direction

Three panes, one hairline system

The redesign changes the frame, not the vocabulary. Everything below is built from tokens already in globals.css — bg-surface, fg-tertiary, accent-primary, the .kairos-system-card hairline-plus-blur treatment, the 16px card radius, the accent gradient reserved for the user's own messages. Nothing new enters the palette.

Three structural moves carry the change: a rail that finally shows state — unread, presence, mute, project origin — instead of repeating each contact's email beneath their name; a thread where every message carries its own delivery status inside a day-grouped, sender-grouped rhythm; and a details pane that gives shared files, pinned messages and mute controls a home so they stop hiding in an overflow menu.

Data model

One new table unlocks most of it

Almost every gap above traces back to the same root: direct_conversations stores participants as two columns on the conversation itself, so there is nowhere to hang per-person state. Adding conversation_participants gives read pointers, mute, archive and clear-history a home — and turns group threads into a data change rather than a rewrite.

TableChangeServes
conversation_participants new conversation_id, user_id, role, last_read_message_id, muted_until, archived_at, cleared_before, joined_at, left_at Unread counts, read receipts, mute, archive, safe delete, leave, group membership
direct_message_attachments new message_id, url, name, mime, size_bytes, width, height Typed attachments; retires the regex parser in the render path
direct_message_reactions new message_id, user_id, emoji — unique on all three Reactions, with toggling enforced by the constraint
direct_messages add reply_to_id, edited_at, deleted_at, pinned_at, pinned_by, body_tsv Replies, edit and delete, pins, in-thread search
direct_conversations add kind ('direct' | 'group'), title, created_by; keep user_one_id / user_two_id through the migration, then drop Group threads without breaking the existing pair lookup

Migration note

Backfill conversation_participants from the two existing columns and keep normalizePair working against them for one release, so getOrCreateDirectConversation stays correct. Then switch the uniqueness check to a participant-set lookup and drop the columns. Nothing here needs a downtime window.

Contract

tRPC and socket surface

Procedure / eventKindNotes
chat.markReadmutation{ conversationId, messageId } — advances the read pointer and never rewinds it. Fires on thread open, on window focus, and on a new message while focused.
chat.getUnreadTotalqueryA single number for the nav badge.
chat.setConversationPrefsmutationMute, archive, pin-to-top — one mutation, partial payload.
chat.toggleReactionmutationInsert-or-delete on the unique triple; returns the new aggregate for the message.
chat.editMessage · chat.deleteMessagemutationAuthor-only, with a time window on edit. Delete writes a tombstone rather than removing the row.
chat.searchMessagesqueryScoped to one conversation or all of them; returns message id and conversation id for deep-linking.
chat.leaveConversationmutationSets left_at. Replaces the destructive deleteConversation.
chat.clearHistorymutationMoves cleared_before forward for the caller only.
message:readsocketTo the conversation room: { conversationId, userId, messageId }.
message:updatedsocketCovers edit, delete and pin with one payload shape.
message:reactionsocketMessage id plus the new aggregate — never a delta, so a duplicated or dropped frame can't desync the count.
presence:updatesocketOrg room, debounced 3s on disconnect so a page refresh doesn't blink the dot.

Two rules keep the client cache honest, both extending patterns ChatClient already uses. Every socket payload carries enough state to be applied idempotently — reactions send the aggregate, not +1 — because the existing dual fan-out means any frame can arrive twice. And every mutation that a socket event also reports gets the same duplicate guard as hasMessage.

Mobile

One pane at a time

The rail and thread collapse to a route-driven single pane below sm: /chat is the list, /chat/[conversationId] is the thread. Making it a route rather than a state toggle fixes the back button, makes notification deep-links land correctly, and lets the thread render on the server. The details pane becomes a sheet.

One thing to fix first: globals-mobile.css applies [class*="w-80"] { width: 100% !important } and collapses all p-6 padding globally. The chat panes need to opt out, or the composer and rail fight the cascade on every small screen.

Delivery

Five phases, shippable in order

Ordered so each phase is independently releasable and the two correctness bugs land first. The visual redesign sits in the middle rather than at the front, because it depends on the read-state data existing before there is anything new to render.

01

Stop the bleeding correctness

Replace deleteConversation with leaveConversation and clearHistory. Gate the notification insert on recipient presence and mute state, and coalesce per conversation. Swap the composer input for a textarea. No visual change ships here.

02

Participants & read state migration

Add conversation_participants and backfill it. Ship markRead, getUnreadTotal, the message:read event, and mute/archive. Unread badges appear in the rail and on the nav — the first user-visible win.

03

The redesign ui

Rebuild the shell as the three panes above. Split the 1011-line ChatClient into ConversationRail, MessageThread, MessageBubble, Composer and ConversationDetails; the cache helpers stay where they are. Route-driven mobile, day and sender grouping, seen receipts, failed-send retry, per-thread drafts, keyboard and aria-log work. Delete the unused ChatPageTabs.tsx.

04

Rich messages content

Typed attachments — retiring the regex in the render path — plus reactions, replies, edit and delete, pins, and presence dots. The details pane fills with real content at this point instead of being a placeholder.

05

Search & groups scale

Postgres full-text over message bodies, server-side conversation search, deep links to a specific message, then group threads and mentions on top of the participants table. Link previews if they still feel worth it.

Open questions

Decisions this proposal doesn't make

  • Read receipts as a setting? Some teams want them off. Cheap to add as a user preference now, awkward to retrofit once people expect Seen to be reliable.
  • Message retention. Nothing prunes direct_messages today. Worth deciding before the table gets large enough that the decision becomes a migration.
  • AI chat's place. /chat/ai is a separate route with its own rail, and ChatPageTabs was written to merge the two but is never rendered. Merge them, or keep the split and delete the dead component? This proposal assumes the split stays.
  • Project-scoped threads. The schema already carries project_id and organization_id on conversations, and listProjectConversations exists — but /chat ignores both. The rail's project tags assume they get surfaced; confirm that's wanted.
