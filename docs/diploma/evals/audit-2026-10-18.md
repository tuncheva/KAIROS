## 1. The persona eval (my work)

- Two runs (`…-run1`, `…-run2`, Markdown + JSON) and [the findings](persona-desi-findings-2026-10-17.md).

**Errors found and corrected in this audit**
- **The tally was wrong.** The findings said "4 of 9 criteria pass", but the table under it shows 2 full passes (C3, C8) and 1 partial (C4). Both docs now say so.

**Errors found and corrected during the work (already disclosed in the findings)**
- The first launch used `pnpm eval:live -- <file>`. The `--` made vitest drop the file filter, so the 55-case routing eval started alongside. I stopped it, killed its orphaned processes and deleted its partial reports. The harness header now says to run without `--`.
- Run 1 had two broken checks. The duplicate detector missed "Получи разрешително…" against the existing "Разрешително…", and the due-date window penalised the post-event photo tasks the persona asked for. Both were fixed before run 2, and run 1 was graded by hand.

**Known limits (not errors, but they bound what the results mean)**
- One model (`gpt-oss-20b`, free NIM tier) and two repeats, so the rates are indicative.
- The tool stubs are coarse. `listTasks` ignores filters, `getTaskDependencies` always returns task 101, and the `searchWorkspace` stub matches loosely, so a tool-selection mistake can be hidden by a generous stub.
- A2 and A4 are driven directly, not through A1's handoff. `handoffContext` and `originalMessage` are never exercised, and that is the path a real user takes.
- C2, C4 and C9 are graded by hand. C9 (3.7/5) is my own judgement.

## 2. A4 event-time fix — `claude/frosty-hopper-29882c`

**What it changes**: 6 files, +264/−92, plus `eventTimes.ts` and two test files.
- The model now writes Bulgarian wall-clock time (`YYYY-MM-DDTHH:mm`). [`eventTimes.ts`](../../../.claude/worktrees/frosty-hopper-29882c/src/server/llm/agents/eventTimes.ts) converts it to UTC on the server, in `Europe/Sofia`, using a new DST-aware `wallClockToUtc` in `src/lib/timezone.ts`. It runs before `applyEventDefaults`, which needs the real instant to compute `endsAt`.
- The prompt now gives today's Bulgarian date, weekday and time, plus a seven-day weekday → date lookup.
- Removed from the prompt: "⚠️ ALWAYS CREATE EVENTS", the Sofia default and the English placeholder description. A missing day or region now produces `creates: []` plus a question.

**Verified**
- `tsc` is clean. Unit suite: 3103 passed and 6 failed. All 6 pass when run alone (80/80): they were timeouts while the A1 suite ran alongside, two of them the known DashboardClient flake.
- The converter on edge cases, called directly:

  | Model writes | Stored (UTC) | Correct? |
  |---|---|---|
  | `2026-11-07T10:00` | `08:00Z` | ✓ EET, after DST ends |
  | `2026-10-22T18:00` | `15:00Z` | ✓ EEST |
  | `2026-10-25T03:30` (occurs twice) | `01:30Z` | ✓ the second occurrence, as documented |
  | `2026-03-29T03:30` (skipped hour) | `01:30Z` = 04:30 local | ✓ shifted past the gap, as documented |
  | `…T10:00:00.000Z` / `…T10:00+02:00` | `08:00Z` | ✓ the zone is deliberately ignored, since the model adds it out of habit |
  | `2026-11-07` (no time) | `10:00Z` = 12:00 local | ✓ |
  | `next Thursday` | passed through unchanged | same as before the fix |

- The persona's a4.* scenarios passed 3/3 on three live runs (the session's report; I read its last report file).

**Issues**
1. **Latency.** The last run's `a4.cleanup-event` took **39.3 s**, against 8–9 s before the fix, which is over the 30 s C8 bar. The prompt is longer now (calendar, rules), but one sample can't separate prompt cost from free-tier noise. Re-measure before calling C8 safe.
2. **`development` touches the same file.** f7ac3f7 adds 2 lines to `a4EventsPublisher.ts`. That's probably a trivial rebase, but this branch was never tested on `development`; the A1 branch was.
3. **A deliberate change from the brief:** times always use `Europe/Sofia`, not the user's timezone setting. The reasoning holds: every region is Bulgarian, and `users.timezone` defaults to UTC, which would bring the bug back. Note it in the thesis as a design decision.
4. **Open, as the session itself reported:** RSVP is switched on for "next Thursday" although nobody asked. A4 still sees only the current message, so the answer to its own date question arrives only through A1's paraphrase. `calendarCreates` is in the schema but never described in the prompt.
5. "Следващия четвъртък" said on a Monday now resolves to this week's Thursday (the 22nd). That is one valid reading; the prompt makes the model write the exact date in the summary, so she can catch it on review.

## 3. A1 grounding fix — `claude/recursing-dubinsky-31ecf5`

**What it changes**: 6 files, +112/−10, plus `a1Grounding.ts` and two test files.
- [`a1Grounding.ts`](../../../.claude/worktrees/recursing-dubinsky-31ecf5/src/server/llm/orchestrator/a1Grounding.ts) is a pure check on A1's parsed output:
  - clarify options naming nothing real are dropped, and the question is rewritten to "no such project; you have: …";
  - a first name shared by two org members forces a clarify;
  - a send-email/SMS request becomes a plain "I can't send that".
- `searchWorkspace` now returns locked notes by **title only** (`locked: true`, empty snippet). The query never selects the content column and has no vector arm.
- The prompt gains rules for not-found, locked notes, same-name people and "cannot send".
- `buildA1Context` now also loads the active org's members.

**Verified**
- `tsc` is clean. Unit suite: 3114 passed and 7 failed. When run alone, all pass except one font test, which is a missing `@fontsource` package in that worktree's `node_modules` (it passes in this checkout).
- The locked-note path keeps the security invariant: no content column, no embedding arm, and the result object is built field by field.
- The session reports the four target scenarios at 2/2 live, also on a copy of `development` with the patch applied.
- Routing eval on the branch: **74.5 %** (41/55) against the 09-25 baseline of 72.7 %. That is not a regression, but the baseline used a different model chain, and "other languages" went from 5/7 to 4/7, which is one case at n = 1.

**Issues**
1. **Lint fails.** `tests/agents/searchWorkspaceLockedNotes.test.ts:113` has an unsafe `any` assignment (error), so `pnpm check` would fail on this branch.
2. **False positive: names that are also words.** I called `findAmbiguousPerson` directly with members Надежда ×2 and Слава ×2. "Има ли надежда да стане навреме?" and "Слава богу, разрешителното дойде" both get turned into "which Надежда/Слава do you mean?". Matching is case-insensitive, and Вяра, Любов, Роза, Злата and Слава are common Bulgarian words. Fix: count only capitalised occurrences.
3. **False positive: "Email notifications for this project — are they on?"** is a settings question, but it becomes "I can't send email". The rule replaces any non-answer output, so a clarify or a handoff the model got right is overwritten.
4. **The wording is too broad.** For "Изпрати съобщение в чата на проекта", the reply is that *KAIROS* has no such capability. KAIROS does have project chat and DMs; only the AI can't send. It should say "I can't send messages for you".
5. **The new prompt rule is false for large workspaces.** "If the name is not in that list, the project does not exist." The list in the context pack is capped at `listProjects({ limit: 25 })`, so for a user with 26+ projects A1 will now deny that real projects exist. Fix: say "not among your 25 most recent — searching…" and fall back to `searchWorkspace`, or lift the cap for names.
6. **The bar was loosened in the eval copy.** The branch dropped the "must call `listProjects` or `searchWorkspace`" check from `a1.unknown-project`. The reasoning is defensible (the list is in the prompt), but combined with issue 5 it removes the one check that would catch the cap.
7. **An extra DB round-trip on every A1 turn.** `listOrgMembers` runs after the parallel batch, not in it, so every turn pays it in sequence. It's small, but it is on every turn.
8. **Not fixed, and not in scope:** "Създай задача на Елена…" still asks for the project instead of handing off (0/2), as before.
